银行在线开户流程架构设计：API-Led、状态机与异步风控

技术 · 2026-09-06 · 18 分钟阅读
API 架构设计 Java 数据库 分布式系统
文章目录

    在线开户不是一条同步接口：用户可以在 Web 或 Mobile 上分多次填资料，身份核验和风控又依赖外部系统，最终的账户开立还必须防止重复。若把这些动作塞进一次 HTTP 请求，超时、重复提交和外部依赖抖动很快会让流程失控。

    本文设计一套以 Java 和 MongoDB 为主的参考实现。这里的 EAPI 指 Experience API：它面向 Web 和 Mobile 提供渠道友好的接口；开户本身作为一个独立的 application 被持久化，并由状态机持续推进。文中名称和规则均为泛化示例，不代表任何银行的真实开户政策。

    一、目标与边界

    这套流程需要同时满足四个目标：

    • 用户可保存草稿、断点续填，前端能随时查询当前进度和待补材料；
    • 提交资料后，身份、人脸、联系方式和反欺诈等检查可以异步执行、失败重试；
    • 任一检查的回调重复到达，或用户反复点击提交，都不能多开账户；
    • 每次状态变化都能追溯到触发来源、规则版本和关联请求，便于运营处理和审计。

    账户的最终账务归属仍应在银行核心系统。本文的开户服务只负责申请编排、风险决策以及向核心系统发起“创建客户/账户”的受控请求，不把 MongoDB 当作账务数据库。

    二、为什么开户场景适合 API-Led

    银行线上开户通常同时连接渠道、客户主数据、身份认证、人脸与证件服务、反欺诈、征信、风控和核心账户系统。这些系统的协议、可用性和变更节奏各不相同；如果 Web/Mobile 直接拼接它们的接口，某一个供应商字段或核心系统报文的变化，就会牵动所有渠道。

    API-Led 的核心不是把每个接口机械地拆成三层，而是按变化原因划分职责：底层系统能力由 System API 封装，跨系统的开户流程由 Process API 编排，渠道展示与交互差异由 Experience API（EAPI）承担。这样既能复用同一套开户流程，也能把遗留核心系统和第三方供应商的复杂性留在边界内。

    在本例中，可以这样理解三层：

    • System API：提供“提交人脸核验”“查询征信”“创建核心账户”等稳定能力，并负责供应商协议、鉴权、超时和字段转换；
    • Process API：拥有 application、状态机、检查编排和决策矩阵，决定申请下一步该做什么；
    • EAPI：服务 Web/Mobile，例如把进度和待办项组织为适合页面显示的 DTO，而不暴露风控供应商的原始结果。

    三、总体架构：按 API-Led 划清职责

  - Application 聚合、状态机、编排、幂等控制
       |----------------------|
       v                      v

  - Application MongoDB      - 延迟任务扫描器或任务队列
  - KYC/人脸供应商           - Outbox 事件发布器
  - 风控/反欺诈              - 回调消费与重试

    EAPI 不直接读取 MongoDB，也不让 Web/Mobile 理解外部供应商的状态。它只把渠道请求转换为稳定的开户契约，例如“保存身份证资料”“提交申请”“获取待办项”。这样将来替换 App 页面、增加合作伙伴渠道，或迁移人脸供应商时，变化被限制在对应的一层。

    Process API 才是业务事实的拥有者。它判断资料是否齐全、当前状态能否迁移，并创建后续检查任务；System API 封装外部系统协议、鉴权和字段映射，避免核心系统的复杂性泄漏到开户流程中。

    四、银行线上开户的一般流程

    不同地区、产品和监管要求会改变具体材料与检查项，但一条典型的线上开户旅程可以按下面的顺序组织。本文将候选客户标识命名为 prospectId：它用于将用户的登录会话、草稿和后续申请关联起来，并支持中断后继续。

    创建申请与网银登录凭据
  -> 设置 PIN 码
  -> 生成并绑定 prospectId（可恢复会话）
  -> 人脸活体与证件识别：第一轮 KYC/反欺诈检查
  -> 补充个人收入、职业、税务居民身份、住址等资料
  -> 提交申请，触发状态机
  -> 异步调用风控、征信及其他合规检查
  -> 决策矩阵：通过 / 补件 / 人工审核 / 拒绝
  -> 创建核心账户并激活网银账号

    “新建网银账号”应理解为创建线上访问身份或预注册凭据，而不是立即建立可用的银行账户。PIN 只能交给专用身份认证系统或 HSM 处理、保存为不可逆的受保护凭据；开户申请与 MongoDB 中不保存 PIN 明文、可逆密文或日志副本。最终的账户开立成功后，再将网银身份绑定到客户和账户并激活使用权限。

    prospectId 不应只放在浏览器内存中。服务端将它映射到 applicationId、用户身份和有效期；客户端可安全保存短期恢复令牌。用户重新登录或更换设备时，EAPI 根据身份与恢复令牌查询同一申请，返回当前状态和待办项。恢复令牌被撤销、过期或身份不匹配时，必须重新认证，而不是仅凭一个 URL 参数继续。

    五、把开户申请建模为聚合

    每位用户发起开户时创建一条 applications 记录。不要因为资料还不完整就等到提交时才创建：草稿本身也是要恢复、限流和审计的业务对象。

    新客开户时，线上登录主体、候选客户与核心客户不是同一个概念：ownerSubjectId 是身份认证系统中的登录主体，prospectId 是开户过程中的候选客户标识，而 coreCustomerId 只在核心客户创建完成后才有值。显式区分它们，可以避免把“已注册网银”误当成“已在核心系统建客户”。

    敏感字段不应以明文出现在日志、事件或普通索引中。身份证件影像、人脸模板等高敏材料更适合存到受控的对象存储或专用 KYC 系统，MongoDB 只保存受控引用、摘要和核验结果。常用索引至少包括 { ownerSubjectId, status }、{ prospectId }、{ status, nextActionAt }，以及核心开户请求的唯一索引；身份证号等受监管字段是否可检索，应通过令牌化或确定性加密结合合规要求设计。

    六、状态机：状态表达业务阶段，检查表达细节

    申请的主状态不需要为每一个供应商调用都增加一个枚举。主状态描述用户和运营最关心的阶段；checks 记录各项检查的细粒度结果。

    DRAFT
  -> IDENTITY_CHECKING         人脸与证件的第一轮检查
  -> COLLECTING_FINANCIAL_INFO 收集收入、地址等资料
  -> READY_TO_SUBMIT           资料完整
  -> SUBMITTED                用户确认提交
  -> WAITING_CHECKS           等待身份/联系方式/人脸结果
  -> RISK_REVIEW               基础检查通过，执行风控
  -> OPENING_ACCOUNT           风控通过，调用核心系统
  -> ACCOUNT_OPENED            核心系统确认成功

任意可处理状态 -> NEEDS_INFORMATION  缺少资料或可补正失败
任意检查阶段     -> MANUAL_REVIEW      命中人工审核规则
任意终态前阶段   -> REJECTED           不可接受的核验/风控结论
OPENING_ACCOUNT  -> OPEN_FAILED        可恢复的技术失败，等待重试或人工处理

    状态迁移要集中在一个组件内，而不是散落在 Controller、回调处理器和定时任务中。每次迁移同时写入 application_events 审计记录，内容至少包含 eventId、fromStatus、toStatus、原因码、操作者/系统名、关联请求 ID 与规则版本。为 { applicationId, eventId } 建唯一索引；重复回调或工作流重放先按它去重，再决定是否更新状态。

    public void transition(Application app, ApplicationStatus target, TransitionContext ctx) {
    if (!stateMachine.canMove(app.status(), target, ctx)) {
        throw new IllegalStateException("invalid application transition");
    }
    applicationRepository.compareAndSetStatus(
        app.id(), app.version(), app.status(), target, ctx.eventId(), ctx.now());
    eventRepository.append(ApplicationEvent.transition(app, target, ctx));
}

    示例中的 compareAndSetStatus 以 _id + version + 当前状态 为条件更新，并原子记录 lastAppliedEventId。它避免两个并发回调都认为自己赢得了状态迁移；更新失败的一方重新读取申请，再根据当前状态和事件 ID 判断该回调是否已经被处理。

    七、从填写到开户的一条完整链路

    1. 创建申请、网银身份与可恢复会话

    POST /v1/onboarding/applications 创建 DRAFT、候选客户 prospectId 和待激活的网银身份；设置 PIN 的请求直接交给身份认证 System API。各页面使用 PATCH /v1/onboarding/applications/{id} 写入资料或人脸会话引用。写操作携带 Idempotency-Key，服务端将“请求键—请求摘要—响应”保存一段时间，网络重试会返回原响应而不是制造多条申请。

    第一轮先执行证件 OCR、证件真实性与人脸活体/比对；通过后进入收入、职业、地址等资料采集。每次保存后由 Process API 计算资料完整度。完整时迁移至 READY_TO_SUBMIT，否则返回明确的 missingItems，例如 PHONE_OTP、FACE_LIVENESS 或 RESIDENTIAL_ADDRESS。前端只依据这份待办清单渲染，不自行复制资格规则。

    2. 用户提交：先固化，再异步启动

    POST /v1/onboarding/applications/{id}/submit 只接受 READY_TO_SUBMIT 状态。它在一个 MongoDB 事务中完成三件事：将状态改为 SUBMITTED、冻结本次核验所需的资料快照、写入待发布的 outbox 事件。事务提交后立刻返回 202 Accepted 与申请 ID，客户端再通过查询或推送获取进度。

    submit
  -> SUBMITTED + outbox: ApplicationSubmitted
  -> WAITING_CHECKS
  -> identity/contact/face 检查任务
  -> 所有基础检查通过
  -> RISK_REVIEW
  -> 风控通过
  -> OPENING_ACCOUNT
  -> 核心账户系统
  -> ACCOUNT_OPENED

    Outbox 使“数据库已经显示已提交，但消息没有发出去”不再依赖侥幸。发布器持续读取未投递事件并发布到消息系统；消费者必须按 eventId 去重，即使消息系统提供至少一次投递也不会重复推进状态。

    3. 延迟等待与检查结果

    资料提交后的等待时间不要用 JVM 内存里的 ScheduledExecutorService 作为唯一机制：应用重启、扩容或任务执行期间故障都会丢失计时。提交时写入 nextActionAt = submittedAt + waitWindow，由持久化任务系统在到期后投递 StartRiskAssessment；也可以用一个带 { status, nextActionAt } 索引的扫描器领取到期任务。

    领取必须是原子的，例如以 findOneAndUpdate 将任务从 READY 改为 RUNNING 并设置租约。工作节点崩溃后，租约到期的任务回到可领取状态。等待窗口内，身份、人脸或联系方式回调可提前更新 checks；到期任务依据聚合结果决定继续风控、补件、人工审核或拒绝，而不是假设每项检查都一定完成。

    4. 风控与账户开立

    风控调用使用申请 ID 作为业务关联号，并保存供应商版本、输入快照摘要、决策码和原始响应的受控引用。规则拒绝转 REJECTED；不确定或需要人工判断的结果转 MANUAL_REVIEW，不要为了自动化强行作出拒绝结论。

    进入 OPENING_ACCOUNT 时先生成不可变的 openRequestId。对核心账户 System API 的每次重试都带同一个请求号，核心侧也应以此实现幂等：同一请求要么返回原账户号，要么表明仍在处理中，绝不能创建第二个账户。只有收到核心侧的最终成功确认后，申请才迁移到 ACCOUNT_OPENED。

    八、决策矩阵：把检查结果变成可审计的决定

    风控、征信和 KYC 的返回值往往不止“成功/失败”。不要把这些条件写成散乱的 if/else，而应由 Process API 将检查结果归一化，再交给版本化的 Decision Matrix（可实现为规则表、DMN 决策表或受控规则服务）给出动作。规则输入只包含必要的事实与原因码，不直接向前端暴露供应商原始响应。

    条件示例 决策 状态机动作
    证件、人脸、联系人、风控和征信均通过 通过 OPENING_ACCOUNT
    人脸清晰度不足、地址缺失等可补正问题 补件 NEEDS_INFORMATION
    风险分数处于灰度区间、征信结果需解释 人工介入 MANUAL_REVIEW
    证件失效、活体失败或明确命中拒绝规则 拒绝 REJECTED
    供应商超时或返回不确定 延迟决定 保持检查中并重试/查询

    每次执行都要保存 decisionVersion、使用到的输入摘要、命中的规则 ID、原因码与最终动作。这样规则调整后，才能解释某个历史申请为什么进入人工审核，也能用历史样本回放评估新规则，而不会重跑第三方核验。

    九、托管状态机方案：AWS Step Functions 与 Lambda

    如果系统部署在 AWS，状态机不必完全自行实现。可以使用 AWS Step Functions Standard 保存长流程的执行进度：Task 状态调用 Lambda 或 Java 服务适配器，Choice 根据归一化检查结果和决策矩阵分支，Wait 表达提交后的等待窗口，Retry/Catch 统一处理可重试与异常路径。对需要等待供应商异步回调的步骤，可使用任务令牌模式：启动检查后暂停执行，回调经受认证的入口恢复对应执行。

    Step Functions Standard
  -> Lambda：启动 KYC / 保存检查引用
  -> 回调任务令牌：等待人脸、证件结果
  -> Lambda 或 Java Process API：收集收入、地址资料状态
  -> Wait：提交后的等待窗口
  -> 并行 Task：风控、征信、反欺诈
  -> Lambda：执行 Decision Matrix
  -> Choice：开户 / 补件 / 人工审核 / 拒绝
  -> Task：调用核心账户 System API 并激活网银身份

    托管编排并不替代业务数据模型：MongoDB 中的 application 仍是对外查询和审计的业务事实，每一个 Step Functions 状态变化也应通过 Process API 以乐观锁写入申请及事件记录。Lambda 与核心账户、征信等有副作用的接口仍必须携带 applicationId、openRequestId 和幂等键；工作流重试或人工重新驱动时，不能依赖“状态机只会运行一次”来避免重复开户。

    工作流的输入、输出和任务令牌载荷只应传递 applicationId、受控对象引用、状态及无敏感含义的原因码；身份证号、影像、人脸结果、详细住址和收入资料仍由 Process API 按需读取。Standard Workflow 的执行历史会保存状态输入和输出，CloudWatch 日志也可以记录执行数据，因此生产环境应按最小权限配置访问，采用客户管理 KMS 密钥，并将日志的 includeExecutionData 设为 false 或只记录已脱敏内容。官方文档对执行历史和日志、数据静态加密和任务令牌回调有具体说明。

    工作流与申请状态的恢复和对账

    Step Functions 的执行状态与 MongoDB 的申请状态分别持久化，二者不能假设天然一致。启动工作流使用确定性的执行名称（例如 applicationId），并立即将返回的 executionArn 写入申请；写入失败时，对账任务可按该名称定位执行。每个任务完成时，由 Process API 以 eventId + version 原子写入申请和审计事件。对于“工作流已推进但数据库更新失败”或“数据库已更新但工作流超时”的情况，定期对账任务按 executionArn 查询执行结果、比对申请的 lastAppliedEventId 与状态，并以同一事件 ID 安全补偿或标记人工处理。人工重驱动也必须复用原有的 openRequestId，而非创建新的开户请求。

    当流程仅包含短任务、无需长期等待且团队已有消息平台时，Java 服务内的状态机与持久化任务也完全可行。选择 Step Functions 的主要理由是减少长等待、重试、可视化追踪和失败恢复的基础设施维护，而不是改变上述领域边界。

    十、失败、重试与人工介入

    外部调用失败不等于业务失败。建议把结果分为三类：

    • 业务终态：证件无效、活体失败、风险拒绝，记录原因码并转 REJECTED 或 NEEDS_INFORMATION；
    • 可重试技术错误：超时、限流、5xx，按指数退避重试，并保留最大次数与下一次执行时间；
    • 不确定结果：请求超时但供应商可能已受理，先用关联号查询结果；无法确认时转人工队列，不能直接重发一个会产生副作用的开户请求。

    运营后台应能查看状态历史、检查摘要、失败原因、下次重试时间和人工处理意见。人工批准/拒绝也必须走状态机并留下操作者与理由；直接修改 MongoDB 文档会破坏审计链。

    十一、接口、可观测性与安全要点

    对外可以保持一组很小的接口：创建申请、保存资料、启动/提交人脸会话、提交申请、查询申请、查询待办项。所有响应带 applicationId、主状态、检查摘要和对前端安全的下一步动作；供应商错误、风控规则细节和账户系统报文不应直接下发。

    每次请求和异步任务都携带 correlationId 与 applicationId。监控中至少关注申请从提交到开户的耗时、各检查通过率、任务积压、回调重复率、状态迁移失败率、工作流与申请状态不一致数量，以及核心开户不确定结果数量。日志采用脱敏字段；访问申请详情需按最小权限控制，并对高敏读取单独审计。对于 Step Functions，执行历史、控制台查看权限、CloudWatch 日志和 KMS 解密权限也应作为同一套敏感数据访问边界治理。

    十二、落地时最容易踩的坑

    1. 把状态机当作前端流程图。 前端可以显示步骤，但最终迁移只能由服务端依据持久化状态决定。
    2. 只靠消息顺序保证正确性。 回调和消息可能重复、乱序或延迟，消费者必须依据版本、状态和事件 ID 判断是否仍有效。
    3. 提交后同步等待所有检查。 HTTP 超时会把正常的异步工作误判成失败，也会占满应用线程。
    4. 把“开户成功”写在调用核心系统之前。 必须以核心侧可查询的最终结果为准，并用请求号保障幂等。
    5. 让 MongoDB 承担账务。 MongoDB 很适合申请聚合、进度和审计索引；余额、分录和账户权威状态仍应由核心账务域负责。
    6. 把 PII 放进工作流载荷。 工作流编排只传申请标识和受控引用；否则执行历史、日志和调试界面都会扩大敏感数据的暴露面。

    结语

    这套设计的重点不是引入更多中间件，而是把三个事实保持一致：申请的持久化状态、异步任务的执行状态，以及核心系统的账户状态。API-Led 划分了集成边界，状态机约束了业务演进，持久化任务、Outbox 和幂等键则让流程能承受超时、重试和重复消息。

    当这些基础能力具备后，新增一项检查通常只是扩展 checks、任务和迁移规则，而不需要重写整个开户接口。这也是把开户建模为长期运行的业务流程，而不是“一次提交表单”的价值所在。
