银行在线开户流程架构设计：API-Led、状态机与异步风控

技术 · 2026-09-06 · 22 分钟阅读
API 架构设计 Java 数据库 分布式系统
文章目录

    在线开户不是一条同步接口：用户可以在 Web 或 Mobile 上分多次填资料，身份核验和风控又依赖外部系统，最终的账户开立还必须防止重复。若把这些动作塞进一次 HTTP 请求，超时、重复提交和外部依赖抖动很快会让流程失控。

    本文设计一套以 Java、MongoDB 和 AWS Step Functions Standard 为主的参考实现。EAPI（Experience API）面向 Web 和 Mobile 提供接口；开户服务在用户提交前管理资料采集和首轮核验，提交后启动云工作流，完成后续检查、决策、核心开户和网银激活。每次申请以 application 持久化。文中规则用于说明设计，具体检查项由产品和适用政策决定。

    一、目标与边界

    这套流程需要同时满足四个目标：

    • 用户可保存草稿、断点续填，前端能随时查询当前进度和待补材料；
    • 提交资料后，风控、反欺诈及产品要求的征信检查可以异步执行、失败重试；
    • 任一检查的回调重复到达，或用户反复点击提交，都不能多开账户；
    • 每次状态变化都能追溯到触发来源、规则版本和关联请求，便于运营处理和审计。

    账户的最终账务归属仍应在银行核心系统。本文的开户服务只负责申请编排、风险决策以及向核心系统发起“创建客户/账户”的受控请求，不把 MongoDB 当作账务数据库。

    二、为什么开户场景适合 API-Led

    银行线上开户通常同时连接渠道、客户主数据、身份认证、人脸与证件服务、反欺诈、征信、风控和核心账户系统。这些系统的协议、可用性和变更节奏各不相同；如果 Web/Mobile 直接拼接它们的接口，某一个供应商字段或核心系统报文的变化，就会牵动所有渠道。

    API-Led 的核心不是把每个接口机械地拆成三层，而是按变化原因划分职责：底层系统能力由 System API 封装，跨系统的开户流程由 Process API 编排，渠道展示与交互差异由 Experience API（EAPI）承担。这样既能复用同一套开户流程，也能把遗留核心系统和第三方供应商的复杂性留在边界内。

    在本例中，可以这样理解三层：

    • System API：提供“提交人脸核验”“查询征信”“创建核心账户”等稳定能力，并负责供应商协议、鉴权、超时和字段转换；
    • Process API：拥有 application、状态机、检查编排和决策矩阵，决定申请下一步该做什么；
    • EAPI：服务 Web/Mobile，例如把进度和待办项组织为适合页面显示的 DTO，而不暴露风控供应商的原始结果。

    EAPI 不直接读取 MongoDB，也不让 Web/Mobile 理解外部供应商的状态。它只把渠道请求转换为稳定的开户契约，例如“保存身份证资料”“提交申请”“获取待办项”。这样将来替换 App 页面、增加合作伙伴渠道，或迁移人脸供应商时，变化被限制在对应的一层。

    Process API 才是业务事实的拥有者。它判断资料是否齐全、当前状态能否迁移，并创建后续检查任务；System API 封装外部系统协议、鉴权和字段映射，避免核心系统的复杂性泄漏到开户流程中。

    申请数据库归开户服务所有，Repository 与 MongoDB 事务位于该服务内部。System API 封装外部系统能力，不额外包装一层通用数据库 CRUD 服务。Step Functions 负责调度、等待和重试；Java 领域逻辑负责校验业务迁移、保存结果和作出决策。Lambda 只承担调用适配，避免再维护一套决策规则。

    四、银行线上开户的一般流程

    不同地区、产品和监管要求会改变具体材料与检查项，但一条典型的线上开户旅程可以按下面的顺序组织。本文将候选客户标识命名为 prospectId：它用于将用户的登录会话、草稿和后续申请关联起来，并支持中断后继续。

    创建申请、prospectId 与网银登录凭据
  -> 设置 PIN 码
  -> 绑定可恢复的登录会话
  -> 人脸活体与证件识别：第一轮 KYC/反欺诈检查
  -> 补充个人收入、职业、税务居民身份、住址等资料
  -> 提交申请，启动本轮 Step Functions 工作流
  -> 异步调用风控、征信及其他合规检查
  -> 决策矩阵：通过 / 补件 / 人工审核 / 拒绝
  -> 创建核心账户并激活网银账号

    流程开始时创建的是线上访问身份或预注册凭据。这里的 PIN 指网银登录凭据，由身份认证系统负责验证和保护，开户数据库及日志不保存其内容；银行卡交易 PIN 属于另一套凭据体系。最终的账户开立成功后，再将网银身份绑定到客户和账户并激活使用权限。

    prospectId 不应只放在浏览器内存中。服务端将它映射到 applicationId、用户身份和有效期；客户端可安全保存短期恢复令牌。用户重新登录或更换设备时，EAPI 根据身份与恢复令牌查询同一申请，返回当前状态和待办项。恢复令牌被撤销、过期或身份不匹配时，必须重新认证，而不是仅凭一个 URL 参数继续。

    五、把开户申请建模为聚合

    每位用户发起开户时创建一条 applications 记录。不要因为资料还不完整就等到提交时才创建：草稿本身也是要恢复、限流和审计的业务对象。

    新客开户时，线上登录主体、候选客户与核心客户不是同一个概念：ownerSubjectId 是身份认证系统中的登录主体，prospectId 是开户过程中的候选客户标识，而 coreCustomerId 只在核心客户创建完成后才有值。显式区分它们，可以避免把“已注册网银”误当成“已在核心系统建客户”。

    身份证影像和人脸材料保存在受控系统中，申请只持有引用。常用查询索引包括 { ownerSubjectId, status } 和 { prospectId }；openRequestId 使用只覆盖有效字符串值的部分唯一索引，避免多条尚未开户的申请因 null 值冲突。

    六、状态机：状态表达业务阶段，检查表达细节

    申请的主状态不需要为每一个供应商调用都增加一个枚举。主状态描述用户和运营最关心的阶段；checks 记录各项检查的细粒度结果。

    DRAFT
  -> IDENTITY_CHECKING         人脸与证件的第一轮检查
  -> COLLECTING_FINANCIAL_INFO 收集收入、地址等资料
  -> READY_TO_SUBMIT           资料完整
  -> SUBMITTED                用户确认提交
  -> WAITING_CHECKS            并行执行后续检查并等待结果
  -> DECIDING                  校验结果并执行决策矩阵
  -> OPENING_ACCOUNT           决策通过，调用核心系统
  -> ACCOUNT_OPENED            已确认核心账户号
  -> ACTIVATING_ONLINE_BANKING 绑定并激活网银身份
  -> COMPLETED                 线上开户流程完成

DECIDING -> NEEDS_INFORMATION / MANUAL_REVIEW / REJECTED
NEEDS_INFORMATION -> 相关资料采集或核验步骤 -> READY_TO_SUBMIT
MANUAL_REVIEW -> DECIDING / NEEDS_INFORMATION / REJECTED

    提交前的状态由开户服务随用户操作推进，提交后的异步步骤由 Step Functions 调度。首轮核验失败也按规则进入补件或拒绝。技术故障保留当前业务阶段，在任务记录中写入错误与重试状态；核心调用结果不确定时尤其不能直接转为“拒绝”或重新创建账户。

    补件会产生新的资料快照和评估轮次。系统根据字段依赖使相关检查失效：修改证件需重做关联身份核验，修改收入需重跑依赖收入的检查；未受影响且仍在有效期内的结果可以复用，但要记录复用来源。回调必须匹配检查请求号和当前轮次，旧轮次结果仅保留审计，不能更新当前决策。

    人工审核意见绑定资料版本，批准后回到 DECIDING，重新确认必要检查完整且未过期，再允许开户。审核超时进入运营待办；补件后原工作流结束，新提交启动新轮次，避免两轮同时有权推进申请。

    状态迁移要集中在一个组件内，而不是散落在 Controller、回调处理器和定时任务中。每次迁移同时写入 application_events 审计记录，内容至少包含 eventId、fromStatus、toStatus、原因码、操作者/系统名、关联请求 ID 与规则版本。为 { applicationId, eventId } 建唯一索引；重复回调或工作流重放先按它去重，再决定是否更新状态。

    // 伪代码：所有 Repository 使用同一 MongoDB 事务会话。
public TransitionResult transition(TransitionCommand cmd) {
    return mongoTransaction.execute(() -> {
        var prior = eventRepository.find(cmd.applicationId(), cmd.eventId());
        if (prior != null) {
            prior.requireSameCommand(cmd); // 同一个事件 ID 不接受不同内容
            return prior.result();
        }
        var app = applicationRepository.get(cmd.applicationId());
        app.requireCurrentRun(cmd.runId());
        stateMachine.requireAllowed(app, cmd.target());
        boolean changed = applicationRepository.compareAndSet(
            app.id(), app.version(), app.status(), cmd.target());
        if (!changed) throw new ConcurrentTransitionException();
        var result = TransitionResult.of(cmd.target(), app.version() + 1);
        eventRepository.insert(cmd, result);
        if (cmd.requiresFollowUp()) outboxRepository.insert(cmd.followUpEvent());
        return result;
    });
}

    条件更新以 _id + version + 当前状态 为条件，并递增版本。去重、状态更新、审计和必要的 Outbox 写入一起提交；任意一步失败都回滚。事件唯一键冲突或可重试的事务冲突发生时，调用方在事务外有界重试整段操作，并重新查询已提交事件。去重依靠事件记录，不能只检查“最后一个事件 ID”。这里要求配置 MongoDB 事务管理及共享会话，并部署在支持多文档事务的副本集或分片集群上。参见 MongoDB 事务文档。

    七、从填写到开户的一条完整链路

    1. 创建申请、网银身份与可恢复会话

    POST /v1/onboarding/applications 创建 DRAFT、候选客户 prospectId 和待激活的网银身份；设置 PIN 的请求直接交给身份认证 System API。各页面使用 PATCH /v1/onboarding/applications/{id} 写入资料或人脸会话引用。写操作携带 Idempotency-Key，服务端将“请求键—请求摘要—响应”保存一段时间，网络重试会返回原响应而不是制造多条申请。

    第一轮先执行证件 OCR、证件真实性与人脸活体/比对；通过后进入收入、职业、地址等资料采集。每次保存后由 Process API 计算资料完整度。完整时迁移至 READY_TO_SUBMIT，否则返回明确的 missingItems，例如 PHONE_OTP、FACE_LIVENESS 或 RESIDENTIAL_ADDRESS。前端只依据这份待办清单渲染，不自行复制资格规则。

    2. 用户提交：先固化，再异步启动

    POST /v1/onboarding/applications/{id}/submit 先检查幂等请求记录，新请求只接受 READY_TO_SUBMIT 状态。在同一 MongoDB 事务中冻结资料快照、生成评估轮次、将状态改为 SUBMITTED，并写入审计事件、幂等响应及 ApplicationSubmitted Outbox 事件。重复请求返回原结果；同一幂等键携带不同内容则拒绝。事务提交后返回 202 Accepted，客户端查询进度。

    submit
  -> SUBMITTED + outbox: ApplicationSubmitted
  -> 启动本轮 Step Functions，验证首轮核验仍然有效
  -> WAITING_CHECKS：并行风控、反欺诈和适用的征信检查
  -> DECIDING：汇总结果，执行决策矩阵
  -> 决策通过
  -> OPENING_ACCOUNT
  -> 核心账户系统
  -> ACCOUNT_OPENED
  -> ACTIVATING_ONLINE_BANKING
  -> COMPLETED

    Outbox 发布器读取未完成的提交事件并启动工作流，成功记录执行关联后再确认事件。启动请求可以重复，因此还需要确定性的执行名称和固定输入，具体恢复方式见第九节。首轮核验结果有效时直接复用，不在提交后无条件重做人脸和证件识别。

    3. 等待结果，而不是等待固定时长

    用户看到的等待时间主要来自异步检查。无依赖的检查并行执行，需要回调的分支等待供应商结果；全部分支结束后才汇总决策。Parallel 会等待分支完成，预期的供应商超时应在分支内通过 Retry/Catch 转为明确的 UNKNOWN 结果，避免一个未处理错误使整个并行步骤失败。参见 AWS Parallel 文档。

    只有业务明确要求延迟、供应商要求稍后查询时才使用 Wait。到期只表示可以再次检查，不意味着风控通过。每个任务有超时和重试上限，耗尽后进入人工处理或受控恢复流程；不得无限等待，也不得把缺失结果当作通过。

    4. 风控与账户开立

    风控调用使用申请 ID 作为业务关联号，并保存供应商版本、输入快照摘要、决策码和原始响应的受控引用。规则拒绝转 REJECTED；不确定或需要人工判断的结果转 MANUAL_REVIEW，不要为了自动化强行作出拒绝结论。

    进入 OPENING_ACCOUNT 时先持久化不可变的 openRequestId。创建核心客户和创建账户分别使用稳定的操作键，并保存每一步的返回标识；任何重试都先复用已有结果。若核心接口不支持幂等，必须提供按业务请求号查询及重复请求控制，不能仅靠本地超时重发。

    确认核心账户号后进入 ACCOUNT_OPENED，再转 ACTIVATING_ONLINE_BANKING，使用独立的激活操作键绑定网银身份。只有激活也成功才标记 COMPLETED。开户和激活无法放入一个本地事务，激活失败时保留账户号，只恢复激活操作。

    八、决策矩阵：把检查结果变成可审计的决定

    风控、征信和 KYC 的返回值往往不止“成功/失败”。不要把这些条件写成散乱的 if/else，而应由 Process API 将检查结果归一化，再交给版本化的 Decision Matrix（可实现为规则表、DMN 决策表或受控规则服务）给出动作。规则输入只包含必要的事实与原因码，不直接向前端暴露供应商原始响应。

    决策前验证结果属于当前轮次，或具有有效的复用记录；过期、来源无法确认的结果不能参与批准。以下示例按从上到下首次命中执行，实际优先级由业务确认。

    优先级 条件 决策与动作
    1 有有效证据命中不可豁免的拒绝规则 REJECTED，其他检查超时不覆盖拒绝
    2 材料缺失、不可读或需用户补正 NEEDS_INFORMATION
    3 必要检查缺失、过期或为 UNKNOWN 有重试额度则回到 WAITING_CHECKS；否则 MANUAL_REVIEW
    4 命中可人工判断的灰区，尚无本版本有效审核意见 MANUAL_REVIEW
    5 必要检查齐全有效，全部满足批准条件（含允许的人工处置） OPENING_ACCOUNT
    默认 未匹配规则或结果组合无法解释 MANUAL_REVIEW，不自动批准

    必要检查由产品配置决定，征信不是所有存款账户都必需。人工意见只能处理授权范围内的灰区，不能覆盖不可豁免拒绝规则或缺失的必要检查。

    每次决策保存规则版本、资料版本、评估轮次、命中规则、原因码和输入快照引用。摘要用于校验一致性；历史回放需要受控保存的实际输入快照，仅有摘要无法恢复输入。回放在隔离评估模式中执行，不触发真实开户。

    九、托管状态机方案：AWS Step Functions 与 Lambda

    本文以 AWS Step Functions Standard 承担提交后的编排：Task 通过 Lambda 调用 Java Process API，Choice 根据决策结果分支，Retry/Catch 处理技术错误，Wait 用于明确的延迟查询。需要等待供应商或人工审核时采用任务令牌回调。Java 服务负责业务迁移校验，工作流不能绕过它直接修改 MongoDB。

    Step Functions Standard
  -> 验证本轮快照与首轮结果的有效性
  -> Parallel：风控、反欺诈、适用的征信检查
       各分支：发起请求 -> 等待回调或查询 -> 保存结果
  -> 调用 Process API：执行 Decision Matrix
  -> Choice
       通过：创建/确认核心客户 -> 创建/确认账户 -> 激活网银 -> COMPLETED
       补件：保存 NEEDS_INFORMATION，结束本轮；重提后启动新轮次
       人工：等待审核 -> 重新校验并决策
       拒绝：保存 REJECTED，结束本轮
       可重试缺失：重跑受影响检查 -> 再次决策

    业务阶段变化由 Process API 写入申请及审计记录。Wait、分支进入等编排细节保留在工作流历史中，不必逐一映射成申请主状态。供应商回调先验证签名、请求号和轮次，持久化结果及待发送的恢复通知，再由内部服务提交任务令牌；令牌不暴露给浏览器。恢复通知可重试，过期令牌不能唤醒新的检查任务。

    工作流的输入、输出和任务令牌载荷只应传递 applicationId、受控对象引用、状态及无敏感含义的原因码；身份证号、影像、人脸结果、详细住址和收入资料仍由 Process API 按需读取。Standard Workflow 的执行历史会保存状态输入和输出，CloudWatch 日志也可以记录执行数据，因此生产环境应按最小权限配置访问，采用客户管理 KMS 密钥，并将日志的 includeExecutionData 设为 false 或只记录已脱敏内容。官方文档对执行历史和日志、数据静态加密和任务令牌回调有具体说明。

    工作流与申请状态的恢复和对账

    每轮评估先持久化执行名称（applicationId + assessmentRunId）、固定输入和工作流版本，再通过 Outbox 启动并记录 executionArn。Standard 的启动幂等适用于同名、同输入且仍在运行的执行；已结束执行会返回 ExecutionAlreadyExists，发布器应查询已有执行并关联，不能改名再启动。参见 StartExecution 文档。补件产生新轮次和新名称；技术重试继续使用原业务操作键。

    每个业务步骤采用稳定的 operationId，由轮次、步骤和逻辑操作序号组成；重试时不随机生成事件 ID。Process API 只有在事务提交后才返回成功。数据库已提交但响应丢失时，重试从去重记录取回原结果；任务尚未提交成功时，工作流不能进入依赖它的下一步。

    对账按执行记录和各步骤操作记录进行，不拿单个“最后事件”判断并行分支是否完成。缺少执行关联时补写 ARN；工作流中断而业务步骤已完成时，恢复调度并复用已存结果；涉及核心账户未知结果时，先按 openRequestId 查询核心系统。工作流显示成功却没有对应业务提交记录属于异常，需要告警和核查，不能据此直接把申请改为成功。

    已有消息平台的团队也可以用 Java 状态机配合持久化任务、租约和调度器替代 Step Functions。它是另一种编排实现；本文主方案不同时维护一套扫描器来推动同一业务步骤。

    十、失败、重试与人工介入

    外部调用失败不等于业务失败。建议把结果分为三类：

    • 业务结果：按规则区分可补正材料问题与明确拒绝，分别转 NEEDS_INFORMATION 或 REJECTED；
    • 可重试技术错误：超时、限流、5xx，按指数退避重试，并保留最大次数与下一次执行时间；
    • 不确定结果：请求超时但供应商可能已受理，先用关联号查询结果；无法确认时转人工队列，不能直接重发一个会产生副作用的开户请求。

    运营后台应能查看状态历史、检查摘要、失败原因、下次重试时间和人工处理意见。人工批准/拒绝也必须走状态机并留下操作者与理由；直接修改 MongoDB 文档会破坏审计链。

    一个恢复实例：账户已开立，网银激活超时

    假设申请 A 的必要检查全部通过，核心系统返回账户号 B，开户服务将其与 openRequestId 一起保存，随后进入 ACTIVATING_ONLINE_BANKING。激活调用超时，既可能未执行，也可能已经生效但响应丢失。

    此时申请显示“账户已开立，网银激活处理中”。恢复任务先查询身份系统的绑定状态；已激活就补记 COMPLETED，未激活则使用原激活操作键重试。超过重试上限交给运营，保留账户 B 和当前阶段，不再调用开户接口。即使整段任务被重新驱动，开户步骤也返回先前保存的账户 B。

    这个例子同样适用于核心开户本身超时：先查询业务请求号，再决定是否重试。只有业务结果明确，才能推进申请状态。

    十一、接口、可观测性与安全要点

    对外可以保持一组很小的接口：创建申请、保存资料、启动/提交人脸会话、提交申请、查询申请、查询待办项。所有响应带 applicationId、主状态、检查摘要和对前端安全的下一步动作；供应商错误、风控规则细节和账户系统报文不应直接下发。

    每次请求和异步任务都携带 correlationId 与 applicationId。监控中至少关注申请从提交到开户的耗时、各检查通过率、任务积压、回调重复率、状态迁移失败率、工作流与申请状态不一致数量，以及核心开户不确定结果数量。日志采用脱敏字段；访问申请详情需按最小权限控制，并对高敏读取单独审计。对于 Step Functions，执行历史、控制台查看权限、CloudWatch 日志和 KMS 解密权限也应作为同一套敏感数据访问边界治理。

    十二、落地时最容易踩的坑

    1. 把状态机当作前端流程图。 前端可以显示步骤，但最终迁移只能由服务端依据持久化状态决定。
    2. 只靠消息顺序保证正确性。 回调和消息可能重复、乱序或延迟，消费者必须依据版本、状态和事件 ID 判断是否仍有效。
    3. 提交后同步等待所有检查。 HTTP 超时会把正常的异步工作误判成失败，也会占满应用线程。
    4. 把“开户成功”写在调用核心系统之前。 必须以核心侧可查询的最终结果为准，并用请求号保障幂等。
    5. 让 MongoDB 承担账务。 MongoDB 很适合申请聚合、进度和审计索引；余额、分录和账户权威状态仍应由核心账务域负责。
    6. 把 PII 放进工作流载荷。 工作流编排只传申请标识和受控引用；否则执行历史、日志和调试界面都会扩大敏感数据的暴露面。

    结语

    这套设计的重点不是引入更多中间件，而是把三个事实保持一致：申请的持久化状态、异步任务的执行状态，以及核心系统的账户状态。API-Led 划分了集成边界，状态机约束了业务演进，持久化任务、Outbox 和幂等键则让流程能承受超时、重试和重复消息。

    当这些基础能力具备后，新增一项检查通常只是扩展 checks、任务和迁移规则，而不需要重写整个开户接口。这也是把开户建模为长期运行的业务流程，而不是“一次提交表单”的价值所在。
