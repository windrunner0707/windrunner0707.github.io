函数式编程：一种优雅但不必迷信的编程方式

技术 · 2026-09-25 · 13 分钟阅读
函数式编程 Java TypeScript 架构设计
文章目录

    第一次接触函数式编程时，我最直接的感受是：代码还能这样写。

    它不急着描述“先修改这个变量，再更新那个状态”。数据从一个函数流向另一个函数，每一步接收输入、完成计算、产生输出。写得好的函数式代码像一条清晰的流水线，也有一点数学推导的工整感。

    不过，FP 并不等于 Lambda、链式调用和一堆陌生术语。理解它的关键，是看清函数、数据与副作用之间的关系。

    函数式编程从哪里来

    函数式编程的源头通常会追溯到 Alonzo Church 在 20 世纪 30 年代提出的 Lambda 演算。它用函数抽象、函数应用和变量替换描述计算。今天 Java、JavaScript 等语言中的 Lambda 表达式，名字就来自这里。

    命令式编程习惯把计算理解为一台机器不断改变内存状态；Lambda 演算提供了另一种视角：计算也可以是表达式的化简，以及函数之间的代入和组合。

    1958 年，John McCarthy 开始设计 Lisp。1960 年发表的论文 Recursive Functions of Symbolic Expressions and Their Computation by Machine 描述了 Lisp 的基本思想。函数、递归和符号处理由此进入了一门真正可以运行的编程语言。

    Lisp 最醒目的语法是 S 表达式：

    (define (square x)
  (* x x))

(map square '(1 2 3 4))

    这段 Scheme 代码把 square 作为参数传给 map，结果是 (1 4 9 16)。程序本身也使用列表结构表示，因此 Lisp 还发展出了“代码即数据”和宏系统。需要说明的是，Lisp 是一个语言家族，Common Lisp、Scheme、Clojure 的设计并不相同；它们有深厚的函数式传统，却不都要求程序保持纯函数。

    后来出现的 ML、Scheme 和 Haskell，又分别推动了类型推导、词法作用域、惰性求值与纯函数等方向。今天，FP 已经进入很多多范式语言：Java 有 Lambda 和 Stream，JavaScript 天生把函数当作值，Scala 则把 OOP 与 FP 放在同一门语言中。

    函数式编程的思想从数学模型进入编程语言，又逐渐成为日常工程工具。

    把 FP 的核心概念放在一起看

    很难用一条规则给所有函数式语言划出边界。Haskell 把纯函数放在语言核心，Lisp 允许直接修改状态，Scala 则是一门明确的多范式语言。它们的选择不同，但共享一些基本倾向：函数是一等公民，数据尽量不可变，计算通过函数组合完成，副作用被放进清楚的边界。

    一等函数与高阶函数

    在函数式编程中，函数不只是依附于对象的方法。它可以像字符串和数字一样赋给变量、作为参数传入，也可以由另一个函数返回。

    const withTax =
  (rate: number) =>
  (price: number): number =>
    price * (1 + rate);

const addVAT = withTax(0.13);
const finalPrice = addVAT(100);

    withTax 接收税率，返回一个新的价格计算函数。这类接收函数或返回函数的函数叫高阶函数。map、filter 和 reduce 也是高阶函数，但 FP 不等于使用这三个 API。真正重要的是，我们可以把“如何计算”本身作为值传递。

    纯函数与引用透明

    纯函数有两个常见特征：相同的输入总能得到相同的输出；执行时不会改变外部可观察状态。

    下面的函数表面上在计算价格，实际还读取全局配置、写日志并修改订单：

    BigDecimal calculatePrice(Order order) {
    var rate = globalConfig.getDiscountRate();
    auditLogger.log(order.getId());
    order.setCalculated(true);
    return order.getAmount().multiply(rate);
}

    只看函数签名，我们不知道它依赖哪些条件，也看不出调用它会改变什么。改成纯函数后，依赖被明确写进参数：

    BigDecimal calculatePrice(
    BigDecimal amount,
    BigDecimal discountRate
) {
    return amount.multiply(discountRate);
}

    纯函数通常具有引用透明性：一个函数调用可以被它的结果替换，而不改变程序含义。calculatePrice(100, 0.8) 如果总是得到 80，理解代码时就不必追查数据库、时间和全局变量。

    这也是纯函数容易测试的原因：

    @Test
void shouldApplyDiscount() {
    var result = calculatePrice(
        new BigDecimal("100"),
        new BigDecimal("0.8")
    );

    assertEquals(new BigDecimal("80.0"), result);
}

    测试不需要启动 Spring 容器，也不用准备数据库和日志组件。输入、规则和预期结果摆在同一个地方，失败后的排查范围自然更小。

    不可变数据

    不可变数据不是说程序里的任何东西都不能变化，而是一次变化产生一个新值，旧值保持原样：

    const rename = (user: User, name: string): User => ({
  ...user,
  name,
});

    如果不同模块都能随手修改同一个 user，排查问题时就要追问它在什么时候被谁改过。返回新值后，状态变化更容易追踪，也减少了共享数据在并发环境中互相干扰的机会。

    不可变并不免费。它可能产生中间对象，也需要语言运行时或持久化数据结构提供支持。在性能敏感的局部代码中，范围明确的可变状态有时更简单。FP 关注的是减少无法控制的共享修改，而不是为了纯粹拒绝一切赋值。

    函数组合与数据管道

    小函数的价值在于组合。假设要处理一批订单，可以把过程写成连续的数据转换：

    const total = orders
  .filter(order => order.status === "paid")
  .map(order => convertToCNY(order.amount, order.currency))
  .reduce((sum, amount) => sum + amount, 0);

    这段代码描述的是“数据怎样变化”，而不是循环变量如何移动、临时集合何时写入。过滤、换算和汇总还能单独测试，并在其他流程中重新组合。

    不过，链式写法只是表象。下面的代码使用了 map，内部却在修改全局变量和访问数据库：

    orders.map(order => {
  globalTotal += order.amount;
  database.save(order);
  return order;
});

    它看起来像 FP，行为仍然很难推理。判断一段代码是否具有函数式价值，应该看依赖是否明确、数据是否被随意修改、每一步能否独立理解，而不是数一数出现了多少次 map。

    副作用与函数式核心

    向数据库保存订单、发送消息、读取文件、获取当前时间，都是副作用。副作用不是错误。一个完全没有副作用的程序，也很难与现实世界交互。

    问题在于，副作用是否和业务计算搅在了一起。一个函数如果同时负责计算优惠、写数据库、发送通知和修改缓存，测试与排错都会变得笨重。

    一种实用的结构是“函数式核心，命令式外壳”：外层读取数据库和系统时间，把明确的数据交给纯函数计算，再把结果写回外部系统。

    var order = orderRepository.findById(command.orderId());
var now = clock.instant();

OrderResult result = calculateOrder(order, command, now, pricingRules);

orderRepository.save(result.order());
eventPublisher.publish(result.events());

    calculateOrder 只负责计算新状态和领域事件。读取、保存与发布仍然存在，但边界清楚了。核心逻辑可以快速进行单元测试，外层则通过集成测试确认数据库和消息系统是否连接正确。

    Monoid 与 Monad：两种关于组合的抽象

    学习 FP 时很快会碰到 Functor、Applicative、Monoid 和 Monad。术语密度突然升高，是很多人觉得 FP 难学的原因。与其先背定义，不如先看它们在解决什么重复问题。

    Monoid：可以稳定合并的值

    Monoid 中文通常译作“幺半群”。它需要一组同类的值、一个合并运算和一个单位元。合并两个值后，结果仍属于同一类；单位元与任何值合并，都不会改变这个值。

    合并运算还需要满足结合律：

    (a <> b) <> c = a <> (b <> c)

    列表是直观的例子。两个列表拼接后仍是列表，空列表 [] 是单位元，先拼左边还是先拼右边不影响结果。字符串与空字符串、整数加法与 0、整数乘法与 1 也有相同结构。

    结合法则并非数学装饰。它意味着大批数据可以被拆成小批分别汇总，最后再合并部分结果。统计聚合、日志拼接和 MapReduce 都能利用这种性质。同一种数据还可以有不同的 Monoid：整数在加法下以 0 为单位元，在乘法下则以 1 为单位元。

    Monad：组合带上下文的计算

    Monad 中文通常译作“单子”。“盒子”或“流水线”的比喻能提供直觉，却无法覆盖所有 Monad。对业务开发来说，从 Result 这样的具体类型入手更容易。

    假设程序要把文本解析成用户编号，再查询用户。两步都可能失败：文本未必是整数，用户也可能不存在。

    type Result<T> =
  | { type: "success"; value: T }
  | { type: "failure"; error: string };

const result = flatMap(parseUserId(input), id => loadUser(id));

    这里传递的不是普通 number，而是 Result<number>。Result 携带了“计算可能失败”的上下文。flatMap 约定：上一步成功，就取出值执行下一步；上一步失败，就保留错误并跳过后面的函数。

    用简化的类型签名表示：

    pure:    A -> M<A>
flatMap: M<A> -> (A -> M<B>) -> M<B>

    pure 把普通值放进某种上下文，flatMap 让返回同类上下文的下一步计算接上来。Result 负责传递失败，Option 负责处理缺失，异步类型则负责等待。

    Monoid 组合值，Monad 组合带上下文的计算。名字相近，两者却不是上下级关系。

    严格来说，只有提供相应操作并满足 Monad 法则的类型才能称为 Monad。这些法则保证改变组合方式时，程序含义不会悄悄变化。入门阶段不必先背完法则，但也不要把所有链式调用都叫作 Monad。

    不同语言里的 FP

    Java：可以实践，但不是围绕 FP 设计

    Java 8 引入 Lambda、Stream 和函数式接口后，函数式风格进入了日常 Java 开发：

    var activeUserNames = users.stream()
    .filter(User::isActive)
    .map(User::getName)
    .sorted()
    .toList();

    函数式接口也让函数可以作为参数传递。不过，Java 不会检查一个函数是否纯净，Stream 中的 Lambda 也完全可以修改外部变量。函数需要借助 Function、Predicate 等接口表达，复杂的类型组合容易变得笨重。

    Java 很适合用来实践纯函数、不可变值和数据转换，但它不会把开发者推向纯函数式设计。

    TypeScript 与 Scala

    TypeScript 中的函数本来就是一等公民，联合类型还能自然地表达不同结果：

    type PaymentResult =
  | { type: "success"; transactionId: string }
  | { type: "failed"; reason: string };

    它适合“实用型 FP”：可以使用高阶函数、readonly、不可变更新和 Result 风格的类型，但语言不会强制纯度与深层不可变。fp-ts、Effect 等库能提供更完整的函数式工具，同时也会增加学习成本。

    Scala 的支持更深入。它有不可变集合、模式匹配和代数数据类型，类型系统也能表达更高级的抽象。Cats、Cats Effect 和 ZIO 等生态把错误、并发和副作用管理带进类型系统。Scala 同时保留类、对象和 Trait，因此它本身就是多范式设计的例子。

    如果想体验以纯函数为默认前提的语言，Haskell 更直接；如果目标是在现有业务项目中改善代码，Java 和 TypeScript 也足够开始。语言会影响表达成本，却不会替团队做出设计选择。

    为什么数据处理特别适合 FP

    数据处理通常就是一组连续的转换：读取、过滤、映射、分组、汇总。只要每个步骤依赖明确，整条流水线就容易拆分和组合。

    纯函数还减少了共享可变状态。如果几批数据之间互不修改对方，就更容易并行执行。MapReduce、Spark 和流处理系统中的 map、filter、fold，都带有明显的函数式思想。

    但并不是只有“大数据”才适合 FP。价格计算、表单校验、权限判断、编译器转换、前端状态更新，同样可以从纯函数和不可变数据中获益。判断标准不是行业，而是问题能否被表达为清楚的数据转换。

    怎样学习，才不容易被术语劝退

    FP 的门槛不只来自概念多，还来自思考习惯的变化。过去我们可能会问：“下一步该修改哪个变量？”函数式的思路更常问：“当前数据经过什么变换，才能得到下一个值？”

    可以按下面的顺序练习：

    1. 学会识别纯计算和副作用；
    2. 把隐藏依赖改成显式参数；
    3. 尽量使用不可变数据；
    4. 用小函数组合数据处理流程；
    5. 用 Option、Either 或 Result 表达缺失与失败；
    6. 遇到反复出现的结构后，再研究 Monoid、Functor 和 Monad。

    《函数式编程图解》适合用来建立直觉。读完以后，可以选一段熟悉的业务代码，把计算逻辑和数据库、日志、时间等外部依赖拆开。这样的练习比先背 Monad 法则更容易形成手感。

    软件工程没有银弹

    函数式编程有一种整洁的美，面向对象也有关于封装、职责和协作的深刻思考。实际系统没有必要在两者之间选边站。

    OOP 更适合描述有身份、状态和生命周期的对象。例如，一个订单从“待支付”变成“已支付”，再进入“已发货”。订单聚合需要保证已取消订单不能支付、已发货订单不能修改地址。这些规则与对象的生命周期紧密相关，放在领域对象中很自然。

    FP 更适合表达定价、优惠匹配、校验和汇总。输入明确、结果稳定的规则可以写成纯函数，不必把所有计算都变成修改对象状态的方法。

    在 DDD 项目中，两者可以这样分工：

    • 用统一语言和限界上下文划分业务边界；
    • 用实体、值对象和聚合维护身份、生命周期与业务不变量；
    • 用纯函数实现规则计算与数据转换；
    • 用状态机约束复杂流程的状态迁移；
    • 用应用服务、仓储和消息适配器管理副作用；
    • 用领域事件连接相对独立的业务流程。

    多范式也不能变成随意拼接。系统仍然要回答：谁拥有状态，哪里允许修改，副作用在哪里发生，失败如何表达，模块之间通过什么契约协作。边界说不清时，使用越多范式，代码反而越乱。

    健壮性并不来自某个术语，而来自可控的变化。领域对象保护业务不变量，纯函数降低计算的不确定性，类型表达可能的失败，状态机限制非法跳转，适配器隔离数据库和网络。当这些职责各自落在合适的位置，代码才更容易测试、理解和修改。

    FP 也有代价。抽象层次过高会增加阅读门槛，不可变数据可能带来额外分配，Effect 系统和复杂类型对团队能力有要求。有些局部算法用一段受控的可变循环，反而比层层函数组合更直接。

    所以，我更愿意把函数式编程看作一套管理复杂度的工具，而不是需要皈依的信仰。学习它的收获，不是把所有代码改写成 FP，而是在面对计算、状态和副作用时，多一种清楚的组织方式。
