面试八股文-线上问题排查

技术 · 2024-10-25 · 9 分钟阅读
面试八股文 性能优化
文章目录

    线上排障不能只背工具名。回答时先说明如何确认影响范围和时间点，再用指标、日志和线程或堆转储验证假设，最后才谈修复。下面以 Java 服务的 CPU、内存和死锁问题为例，并补充 Arthas 与可观测性体系的实战用法。

    1. 先确认现象和影响

    先确认问题从什么时候开始、影响哪些实例和请求，再根据现象判断方向。

    在线上系统中，当 CPU 或内存负载过高时，通常会导致以下现象：

    CPU负载高：请求响应时间增加，服务性能下降，甚至出现服务宕机。

    内存负载高：可能会出现频繁的垃圾回收（GC）操作，尤其是 Full GC，或者出现内存溢出（OutOfMemoryError）。

    死锁问题：程序无响应，线程一直等待，CPU使用率突然降低，系统几乎卡死。

    通过监控工具（如 Prometheus、Grafana、Kibana 等），我们可以实时监控系统的 CPU 和内存使用情况，还可以结合 APM 工具（如 New Relic、Pinpoint）监控请求性能。

    1. 初步诊断

    接下来，我们可以根据不同的现象进行初步诊断，说明会优先查看哪些指标，并使用什么工具。

    可以这样回答：

    CPU 过高时，先用 top 或 pidstat 找到进程，再用 top -H -p <pid> 找到高 CPU 线程。将十进制线程 ID 转成十六进制后，在 jstack 输出中定位对应的 nid，连续采集几次堆栈，判断线程是否反复停在同一段代码。

    对于内存负载过高，我会检查 GC 日志，以判断是否是由于频繁的垃圾回收导致内存回收不及时。JDK 9 及以上使用统一日志参数（如 -Xlog:gc*），JDK 8 才使用 -XX:+PrintGCDetails 等参数。同时可以使用 jmap 命令生成堆内存快照（Heap Dump），并结合 MAT（Memory Analyzer Tool） 来分析哪些对象占用了大量内存。

    对于死锁问题，最常见的是通过 jstack 查看线程堆栈，检查是否有线程处于等待锁的状态。如果是多线程引发的死锁问题，线程堆栈中会显示哪些线程正在等待获得其他线程持有的锁资源。

    1. 深入定位

    初步判断后，继续用连续采样、日志、GC、下游延迟和近期发布记录交叉验证，不要只依赖一份快照。

    CPU 负载高：jstack 不提供线程 CPU 使用率，需要先从系统工具取得线程 ID，再到线程转储中匹配。单次堆栈只是快照，应连续采样，并结合请求量、GC、下游延迟和最近发布记录判断原因。

    内存问题：生成堆内存快照后，我会使用 MAT 等工具分析哪些类或对象占用了大量内存。例如，大量不应长期存活的对象可能意味着内存泄漏；也可以用 jmap -histo 查看 JVM 中各类对象的数量分布，再结合业务场景定位内存热点。

    死锁问题：通过 jstack 可以分析哪些线程进入了死锁状态。如果确认有死锁，通常会在堆栈中看到 Thread-1 等待 Thread-2 的锁，而 Thread-2 又在等待 Thread-1 的锁。此时可以使用线程转储信息（如 jstack 或 jconsole）找到具体的锁争用代码，并通过代码审查或调整锁的顺序来解决死锁问题。

    Arthas：在线验证假设

    Arthas 适合在不重启 Java 进程的前提下查看 JVM、线程、方法调用和对象情况。它的价值不在于把所有命令都跑一遍，而在于用低风险的观察手段验证一个明确假设：例如“慢请求是否集中在某个方法”“某个接口的参数是否异常”“CPU 高是否由 GC 或指定线程引起”。

    常用的起手式如下：

    # 连接目标 Java 进程；生产环境应通过受控主机或容器入口执行
java -jar arthas-boot.jar

# 查看 JVM 概况、内存区域、GC 和线程情况
dashboard
jvm
memory
thread -n 5

# 查看某个类加载自哪个 jar，避免同名类或多 ClassLoader 判断错误
sc -d com.example.order.OrderService

    dashboard 用于快速建立“CPU、堆、GC、线程”全局视图；thread -n 5 可列出 CPU 占用最高的线程，并给出当前堆栈。若看到 GC 线程占比异常，要回到 GC 次数、暂停时间与分配速率判断，不能把业务线程当成唯一方向。

    当链路已经缩小到一个类或方法时，再使用方法级命令：

    # 查看方法调用耗时、异常和返回值；先从有限次数开始
watch com.example.order.OrderService createOrder '{params, returnObj, throwExp}' -x 2 -n 3

# 每 5 秒输出一次调用统计，识别慢方法和异常比例
monitor -c 5 com.example.order.OrderService createOrder

# 仅追踪耗时超过 200ms 的调用路径，避免输出过多
trace com.example.order.OrderService createOrder '#cost > 200' -n 5

# 查看活跃线程的调用栈采样，用于判断热点路径
profiler start
# 等待一段有代表性的业务流量后
profiler stop --format html --file /tmp/order-cpu.html

    watch 会暴露参数、返回值或异常，trace 会打印调用树，二者都可能带来性能开销或泄露敏感业务数据。因此线上应遵守几个边界：先限定类、方法、条件与 -n 次数；不要把密码、令牌、身份证号等写进观察表达式；高流量路径优先用采样和短时间窗口；将导出的火焰图或堆转储按敏感数据处理。问题复现或证据收集完成后及时退出 Arthas 并清理临时文件。

    如果怀疑类加载、连接池或缓存对象异常，也可以先看对象数量再决定是否导出堆：

    # 抽样查看某类实例及字段；结果只是当下快照
vmtool --action getInstances --className com.example.cache.LocalCache --limit 10

# 导出堆前确认磁盘空间、脱敏与上传路径；优先在从实例或隔离环境执行
heapdump /tmp/service-heap.hprof

    注意：vmtool 获取实例和 heapdump 都可能影响线上服务，并且 heap dump 常包含用户数据。它们应是有审批、可回滚、已确认磁盘容量后的动作；vmtool 的少量样本也不能代表全部对象分布。多数场景先用 GC 指标、类直方图和 Arthas 的轻量观察缩小范围。

    可观测性：让排障从“登录机器”变成“沿请求找证据”

    可观测性不是把指标、日志和链路追踪分别装上就结束，而是让三类数据能用同一个请求、实例、版本和时间窗口关联。实践中可以以四个黄金信号组织看板和告警：

    信号 重点指标 排障时要问的问题
    延迟（Latency） P50/P95/P99、下游调用耗时 慢的是全部请求，还是某个接口、租户或依赖？
    流量（Traffic） QPS、消费速率、队列积压 是突发流量、重试风暴，还是流量下降造成的假象？
    错误（Errors） 5xx、业务失败码、超时、异常类型 错误集中在哪个版本、可用区、下游或参数组合？
    饱和度（Saturation） CPU、堆、GC、线程池、连接池、磁盘与队列利用率 哪个有限资源先被打满，排队发生在哪里？

    指标系统（如 Prometheus + Grafana）适合发现趋势、分实例比较和告警；日志系统（如 ELK/OpenSearch）适合检索错误上下文；链路追踪系统（如 SkyWalking、Jaeger、Tempo 或 OpenTelemetry 生态）适合把一次慢请求拆到服务、SQL、缓存和 RPC 调用。选型可以不同，但应统一服务名、环境、区域、实例、版本等标签，避免同一个服务在三套系统中名称不一致。

    日志至少应包含 timestamp、level、service、env、instance、traceId、spanId、requestPath、costMs、errorCode 等可检索字段。入口层生成或透传 traceId，并写入日志 MDC；异步线程、消息队列消费和 RPC 调用也要显式传递上下文。这样看到 P99 升高时，可以从异常或慢请求的 traceId 进入链路，再回到对应实例和时间范围检索日志，而不是在海量日志中猜关键词。

    一次慢请求的实战排查路径

    假设告警显示“下单接口 P99 从 300ms 升到 4s，5xx 未明显上升”，可以按下面顺序处理：

    1. 定边界：确认开始时间、影响比例、接口、地域、版本与实例。对比正常实例和异常实例，避免把全站平均值当作结论。
    2. 看信号关联：在同一时间窗口查看 QPS、错误率、CPU、GC、线程池活跃数/队列长度、数据库连接池和下游延迟。若 QPS 平稳但某个下游 span 变慢，优先查依赖；若线程池队列增长，查阻塞位置和池配置。
    3. 沿 trace 下钻：挑选慢请求的 trace，定位耗时最长的 span；查看它关联的结构化日志和错误码。对数据库调用同时确认慢 SQL、锁等待与连接池等待，不能只看应用总耗时。
    4. 用 Arthas 验证：在一台异常实例短时间执行 thread -n 5、trace 或 monitor，验证热点是否与链路判断一致。观察次数要小，避免在所有实例上同时执行重命令。
    5. 止损与修复：根据证据选择扩容、摘除异常实例、限流/降级、回滚或切流。止损动作之后继续观察同一组 SLI，确认 P99、错误率和饱和度同时恢复；随后修复根因并补回归测试、告警和运行手册。

    这一流程的关键是“假设—证据—结论”：例如“数据库慢”不能只凭接口慢就下结论，至少应有 trace 中的 SQL span、数据库慢查询/锁等待或连接池等待等证据相互印证。

    1. 修复与验证

    先止损并保留现场，再按问题类型修复。调整参数只能缓解症状，不能替代对代码、对象生命周期和锁顺序的分析。

    CPU负载高的解决措施：

    对于热点代码问题，我会优化代码逻辑，避免不必要的复杂计算或耗时操作。对于 IO 密集型操作，可以考虑使用异步处理或批量处理的方式，降低 CPU 占用。

    如果 CPU 消耗来自频繁 GC，应先判断是堆容量不足、对象分配过快还是内存泄漏。调整 -Xmx 或收集器可能缓解症状，但不能替代对分配热点和对象生命周期的分析；CMS 已在较新的 JDK 中移除，不宜再作为通用方案。

    内存负载高的解决措施：

    如果是内存泄漏问题，通常会通过分析堆内存快照找到未及时释放的对象，修复对象生命周期管理中的问题。

    调整堆内存大小，例如通过调整 -Xmx 参数增加堆内存上限，或者通过优化代码减少大对象的创建频率，避免内存占用过高。

    死锁问题的解决措施：

    对于代码中的锁争用问题，我会检查代码中的锁的使用顺序，确保锁的获取顺序一致，避免产生环形等待。如果需要在高并发环境中使用锁，可以使用诸如 ReentrantLock 或使用无锁并发算法来降低锁的使用频率。

    可以通过 tryLock() 方法替代传统的 synchronized 来实现非阻塞锁，并设置合理的超时机制，避免长时间等待锁。

    1. 预防

    日常开发中，把性能检查、内存监控和并发审查放进交付流程，避免每次都等到线上出问题才处理。

    为了避免 CPU、内存负载过高和死锁问题，我们可以采取以下预防措施：

    代码层面优化：定期进行代码审查，关注性能瓶颈，避免无效循环和阻塞操作。在并发编程时，使用更高级别的并发控制工具如 ConcurrentHashMap 或者 ForkJoinPool 来提高并发处理的效率。

    内存管理：通过设置合理的 JVM 参数和使用工具如 JVisualVM、Prometheus 等对应用的内存使用情况进行监控，提前发现潜在问题。还可以引入内存池等机制来管理大对象。

    监控与报警：借助 APM 工具（如 Skywalking、Prometheus 等），实时监控 CPU 和内存的使用情况，设置预警阈值，确保在问题恶化之前就能处理。

    可观测性还应成为日常交付的一部分：为关键接口定义 SLI/SLO（例如可用性、P99 延迟与错误率），告警优先围绕用户影响和错误预算，而非只对 CPU 设单一阈值；每次发布给指标和日志带上版本标签，保留发布事件；为数据库、缓存、消息队列、线程池和连接池配置容量看板；演练一次从告警到 trace、日志、实例诊断再到回滚的流程。这样告警响起时，值班人员拿到的是可执行的排障入口，而不只是“机器负载高”。

    实际处理顺序可以固定为：先止损并保留现场，再确认现象，随后用多份证据定位。CPU 看进程、线程和连续堆栈；内存看 GC 趋势、对象分布和堆转储；死锁看线程等待关系。修复后用相同指标验证效果，并补上能更早发现同类问题的告警。
